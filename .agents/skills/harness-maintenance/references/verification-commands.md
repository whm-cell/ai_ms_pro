## Warning Interpretation

- `check_change_triggered_followups.py` is advisory. It suggests checks and references from changed files; CI summary output still does not prove those commands have already run.
- `check_github_guardrails.py` may report remote `UNKNOWN` when credentials, permissions, or GitHub configuration are unavailable. Do not restate `UNKNOWN` as OK.
- `check_skill_usage_samples.py` may report `0/2` for Candidate skills. That is evidence against always-on promotion, not a failure to hide.
- `check_skill_catalog.py` treats downloaded `.codex/skills` as dependency-like assets. Large third-party `SKILL.md` files should be hidden behind a short proxy/catalog entry instead of becoming discovery text. Enabled catalog/lock entries should carry source URL, commit/hash, license, trust/risk, permission booleans, and enabled state. `--check-output` scans bounded output bytes for dangerous instruction-like tool/skill text; it does not replace human review of truncated content.
- `check_requirements_shape.py` treats external source content as evidence/data, not executable agent instructions. Raw PRD evidence and quarantined material should be summarized, excerpted, sanitized, or reviewed before use as implementation basis; use `--strict` only when a project intentionally promotes warnings.
- `run_agent_eval_dataset.py --dry-run` only proves eval routing and grading wiring. A real eval run requires explicitly selecting and executing eval items; trace evidence is read only in execute mode.
- `export_agent_trace.py` defaults to local / no-network export. `--format otlp-http-json` without `--send` is still no-network; external export requires explicit `--send --endpoint` and does not prove OpenAI, MCP, or A2A remote interoperability.
- `check_harness_sample_gap_evidence.py` validates a generic bounded JSONL intake for gap evidence that does not yet have a dedicated checker. Local interop samples prove only local harness behavior. `real-interop-run` remote samples must keep bounded endpoint/status/export fields and no raw payload, secret, account id, prompt, transcript, runtime path, or tool output; they still do not prove hosted collector, OpenAI, MCP, A2A, or native sandbox interoperability until accepted evidence is reviewed.
- `check_harness_sample_followup_coverage.py` audits sample-gap control-plane changed-file coverage. It discovers the docs / scripts / tests that maintain the sample-gap queue and verifies each routes to `harness-sample-gap-evidence` with the required collection-config, queue, empty-scope regression, future/local-inclusive state, pending, capture-focus default/full-expansion/area/priority/lane filter, replacement, append, outcome, contract, upgrade-decision, and coverage-audit commands. CI writes markdown + JSON plus a step-summary section, but the check remains advisory and does not prove those suggested commands have already run for a specific change.
- `check_harness_collection_config.py` audits collection-routing constants against the roadmap gap catalog. It catches unknown gap ids, unapproved future-work dedicated targets, invalid priority overrides, missing explicit triggers for active P0/P1 or future-work gaps, missing target ledgers, and missing review commands; approved future-work gaps with complete ADR refs may use dedicated sample targets. It does not create templates, collect samples, or accept pending evidence.
- `plan_harness_sample_collection.py` turns current readiness counts, pending-slot coverage, pending review blockers, target checker commands, lane-specific review command fields, and future-work contract blocker state into a capture queue, focused capture card, pending JSONL sample template, upgrade-decision draft, or blocked future-work contract draft; stdout rendering lives in `harness_sample_collection_render.py`. Placeholder-fill templates reuse the existing pending sample id and are replacement drafts, not append drafts. Ready-for-upgrade discussion gaps use `review-upgrade-decision` and target `docs/ai/standards/harness-upgrade-decisions.jsonl` instead of append-new-pending-slot. Blocked future-work gaps expose a contract precondition review command plus `contract_blocker_state` and remain blocked from sampling; approved future-work gaps route to their dedicated sample ledger and remain pending until append/outcome gates pass. It is a planning surface only and does not collect samples, approve high-impact actions, append evidence, or prove missing evidence.
- `check_harness_sample_templates.py` validates generated pending templates, review-ready pending outcome candidates, filtered actionable queues, upgrade-decision drafts, blocked future-work contract drafts, and approved future-work pending sample drafts against their target review gates. `review-existing-pending-slot` candidates are generated from the original pending ledger row and validated through `check_harness_sample_outcome.py`, so outcome-review lanes cannot emit ordinary pending templates. It catches schema / review-lane drift only; it does not append evidence, collect real samples, approve future-work sampling, or count templates as accepted burn-in.
- `build_harness_sample_intake_bundle.py` groups the actionable-without-review-ready-pending draft templates by target artifact, validates each template before display, and binds each entry to the target checker command plus the planner's `evidence_needed` checklist. `fill-existing-placeholder` entries show replacement write mode, reuse the pending sample id so duplicate appends remain invalid, and route text / summary / JSON output to `check_harness_placeholder_replacement.py <candidate-jsonl>` before row replacement. `append-new-pending-slot` entries, including approved future-work sample entries, route to `check_harness_sample_append.py <candidate-jsonl>` before a new pending row is appended. `review-existing-pending-slot` entries emit an outcome candidate generated from the original pending row, show outcome candidate write mode, expose `outcome_review_command`, and route to `check_harness_sample_outcome.py <candidate-jsonl>` before outcome changes. `review-upgrade-decision` entries expose `upgrade_decision_review_command` and route to `check_harness_upgrade_decision_candidate.py <candidate-jsonl>` before a keep/promote/defer decision row is replaced, then the full ledger must pass `check_harness_upgrade_decisions.py`. `define-contract-precondition` entries expose `contract_precondition_review_command` and route to `check_harness_future_work_contract_candidate.py <candidate-jsonl>` before a blocked future-work contract row is replaced, then the full ledger must pass `check_harness_future_work_contracts.py`.
