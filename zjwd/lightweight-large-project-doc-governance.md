# 轻量版大项目文档治理方案

更新时间：2026-04-15

## 目标

本文档定义一套适用于当前项目的“轻量版大项目文档治理方案”。

它的目标不是复制 Jira、Confluence、ADR 平台、知识库和自动检索系统的全量能力，而是在当前仓库内，用尽量少的结构，实现以下效果：

- 控制阶段性文档膨胀
- 保留 AI 和人类执行者都能理解的活跃上下文
- 让长期决策和短期接力信息分层存放
- 让历史信息可追溯，但不污染当前入口

## 核心原则

### 1. 文档必须分层

不同目的的内容不能混写在同一种文档里。

至少应拆分为以下几层：

- 项目级规划层
- 阶段状态层
- 任务接力层
- 版本说明层
- 长期决策层
- 历史归档层

### 2. 低层高频，高层低频

文档层级越低，更新越频繁，生命周期越短。

- `handoff`：高频、短周期
- `status`：中频、阶段级
- `changelog`：阶段级或版本级
- `plan` / `adr`：低频、长期有效

### 3. 治理的核心是压缩，而不是堆积

每一层都不应该无限增长。

治理思路应是：

- 让低层文档不断产生
- 把低层文档压缩进更高层摘要
- 把失活的低层文档移入归档
- 让主入口只指向当前活跃摘要

### 4. 总入口必须稳定

无论是否使用 skill，都必须有一个稳定入口文件，供 AI 和人类快速定位当前有效文档集合。

建议使用：

- `docs/ai/index.md`

## 推荐目录结构

```text
docs/
  ai/
    index.md
    plan.md
    handoffs/
      active/
      archive/
    status/
    changelog/
    adr/
    archive/
```

目录说明：

- `index.md`：当前有效入口
- `plan.md`：项目总计划与边界
- `handoffs/active/`：当前阶段仍在使用的接力文档
- `handoffs/archive/`：退出活跃阶段的接力文档
- `status/`：阶段总结
- `changelog/`：阶段变更说明
- `adr/`：长期有效的架构和关键决策
- `archive/`：其他需要保留但不应放入主入口的历史资料

## 六层文档模型

### 第一层：项目规划层

文件：

- `docs/ai/plan.md`

作用：

- 描述项目目标、范围、模块、阶段、风险、验收标准

更新频率：

- 低频

保留策略：

- 长期保留

### 第二层：阶段状态层

文件：

- `docs/ai/status/stage-01-summary.md`
- `docs/ai/status/stage-02-summary.md`

作用：

- 汇总阶段目标、完成度、风险、阻塞、下一阶段重点

更新频率：

- 每阶段一次或少量补充

保留策略：

- 长期保留，但只把当前和最近阶段放进主索引

### 第三层：任务接力层

文件：

- `docs/ai/handoffs/active/stage-01-auth.md`
- `docs/ai/handoffs/active/stage-01-api.md`

作用：

- 记录当前任务的接续上下文

更新频率：

- 高频

保留策略：

- 当前阶段放在 `active/`
- 阶段汇总完成后移入 `archive/`

### 第四层：版本说明层

文件：

- `docs/ai/changelog/stage-01.md`

作用：

- 沉淀本阶段对外可理解的变更说明

更新频率：

- 阶段收尾或版本准备时

保留策略：

- 长期保留

### 第五层：长期决策层

文件：

- `docs/ai/adr/001-auth-architecture.md`
- `docs/ai/adr/002-api-versioning.md`

作用：

- 沉淀对后续阶段仍长期有效的决策

更新频率：

- 低频

保留策略：

- 长期保留

### 第六层：历史归档层

文件：

- `docs/ai/archive/`
- `docs/ai/handoffs/archive/`

作用：

- 保存可追溯信息
- 避免历史上下文污染当前工作入口

更新频率：

- 随阶段结束而增加

保留策略：

- 不放入主入口，仅提供归档入口链接

## 文档压缩机制

### 压缩链路

推荐采用如下压缩路径：

`handoff -> status -> changelog / adr`

含义：

- 高频任务细节先记录在 `handoff`
- 阶段级结论压缩进 `status`
- 对外变更压缩进 `changelog`
- 长期有效决策压缩进 `adr`

### 压缩原则

- 同一条信息不要长期存在于 3 个以上文档中
- `handoff` 里的大量过程细节不应原样复制到 `status`
- `status` 里的阶段判断不应原样复制到 `changelog`
- 只有长期有效的决策才进入 `adr`

### 归档触发条件

满足以下任一条件时，应考虑归档 `handoff`：

- 对应阶段已经产出正式 `status`
- 对应任务已经完成并不存在活跃后续动作
- 文档中的下一步动作已经失效

### 治理闭环的标准表达

本方案推荐将持续治理明确表达为：

`分层 -> 压缩 -> 归档 -> 保留活跃入口`

这四步缺一不可：

- 没有分层，信息职责会混乱
- 没有压缩，低层文档会无限堆积
- 没有归档，历史信息会污染当前上下文
- 没有活跃入口，AI 和人类都不知道当前先看什么

## `index.md` 的职责

### 为什么需要 `index.md`

因为当前项目缺少更重型的治理系统。

`index.md` 的作用是：

- 为 AI 提供稳定入口
- 为新会话快速定位当前有效文档
- 阻止历史文档干扰当前判断

### `index.md` 不该做什么

不应该：

- 枚举所有历史文档
- 成为全量目录树
- 记录大量过程细节

否则它会从入口文件退化成新的信息噪声源。

### `index.md` 应维护的最小信息

建议只保留：

- 当前阶段
- 当前主目标
- 当前建议优先阅读顺序
- 最新 `plan`
- 最新活跃 `handoff`
- 最新 `status`
- 最新 `changelog`
- 重要 `adr`
- 归档入口

## AI 视角下的入口顺序

建议未来约定 AI 在开始新一轮工作时默认按以下顺序读取：

1. `docs/ai/index.md`
2. `docs/ai/plan.md`
3. 当前阶段最新 `status`
4. 当前活跃 `handoff`
5. 相关 `adr`
6. 必要时再进入归档

这比直接扫描整个 `docs/` 更稳。

## 模板设计依据

### 这次模板是按什么业务线索构建的

这次落地的模板不是按具体业务域构建，而是按“项目推进线索”和“信息生命周期”构建。

主要依据有三条：

#### 1. 按推进阶段组织

模板围绕项目从启动到发布的典型推进过程设计：

- 计划
- 子任务执行
- 阶段汇总
- 变更说明
- 长期决策

也就是说，模板先服务于“项目怎么往前推进”，而不是先服务于某个业务模块名称。

#### 2. 按决策时效组织

不同文档承载不同时间尺度的信息：

- `handoff`：短期、立即接力
- `status`：中期、阶段判断
- `changelog`：阶段或版本成果
- `adr`：长期、跨阶段仍有效的决策

这能减少“短期记录挤进长期文档”的混乱。

#### 3. 按 AI 的消费顺序组织

模板设计考虑了 AI 的典型检索路径：

- 先看全局入口
- 再看项目边界
- 再看当前阶段状态
- 再看具体任务交接
- 最后看长期决策或归档

因此，本次模板本质上是“面向 AI 协作检索”的文档骨架，而不是传统人类项目周报模板。

## 不同阶段如何稳健引入不同 Skill

### 核心原则

Skill 不应该随机出现，而应绑定到文档层和阶段职责。

稳健落地的原则是：

- 每个阶段只引入与当前目标直接相关的 skill
- skill 的输出必须落到对应文档层
- skill 产物必须被高一层文档吸收或压缩
- skill 使用后必须更新活跃入口

### 建议的阶段到 Skill 映射

#### 第 0 阶段：项目启动与规划

目标：

- 明确目标、范围、模块边界、阶段拆分

建议输出：

- `plan.md`
- 必要时生成首批 `adr`

Skill 使用原则：

- 规划类、架构类、技术选型类 skill 可以在这一阶段使用
- 产物必须沉淀到 `plan.md` 或 `adr/`

#### 第 1 到 N 阶段：功能开发

目标：

- 拆分并行任务
- 推进具体实现

建议输出：

- `handoff` 文档
- 阶段完成后生成 `status`

Skill 使用原则：

- 某个 skill 负责具体任务时，其结果先进入 `handoff`
- 多个 `handoff` 的稳定结论再压缩进 `status`

#### 测试、联调、上线准备阶段

目标：

- 汇总功能变更
- 识别风险
- 形成发布前说明

建议输出：

- `status`
- `changelog`

Skill 使用原则：

- 测试类、验证类、发布说明类 skill 可以在这一阶段使用
- 对外变化写进 `changelog`
- 风险和阻塞写进 `status`

### Skill 落地的四个约束

#### 1. Skill 必须有明确落点

每个 skill 在项目内都应回答：

- 它的输出属于哪一层文档
- 谁负责吸收它的结果
- 何时从活跃区退出

如果回答不了，这个 skill 很容易制造文档噪声。

#### 2. Skill 输出不能直接变成长期记忆

skill 运行结果通常先进入低层文档，例如 `handoff`。

只有满足以下条件，才应进入长期层：

- 对当前阶段之外仍有效
- 是稳定决策而不是一次性过程
- 后续执行者需要持续参考

#### 3. Skill 之间不能绕开压缩链路

例如：

- 实现类 skill 不能直接改写 `changelog` 代替 `handoff`
- 一次子任务的结果不应直接当成阶段 `status`

必须遵循：

`skill 输出 -> 对应层文档 -> 高层压缩 -> 更新索引`

#### 4. Skill 使用完成后必须检查入口

每次使用 skill 产生新文档后，都应至少检查：

- 当前活跃文档是否变化
- `index.md` 是否仍指向正确入口
- 是否有旧 `handoff` 应被归档

### 适合本项目的稳健落地方式

对当前项目，推荐这样落地：

1. 用 `session-handoff` 作为子任务结束后的标准记录机制
2. 用 `status-report` 作为阶段结束后的标准汇总机制
3. 用 `changelog-automation` 作为阶段收尾和发布前说明机制
4. 用本地规则或后续自定义 skill 负责 `index.md` 维护
5. 将长期有效的关键结论写入 `adr`

这样每个 skill 都有边界，不会把文档系统搅乱。

## 是否必须依赖 skill

不必须，但如果完全不加约束，AI 不会稳定地在每次对话后主动更新 `index.md`。

可选治理强度如下：

### 方案 A：纯规则

在项目约定中明确：

- 每次有实质性进展后必须检查 `index.md`

适合：

- 项目规模尚小
- 开发者愿意手动监督

### 方案 B：规则 + 模板

在 handoff、status、changelog 模板里明确要求：

- 更新文档后同步检查 `index.md`

适合：

- 中型项目早期

### 方案 C：规则 + 自定义 skill

增加本地 skill，专门负责：

- 判断哪些文档是当前活跃入口
- 更新 `docs/ai/index.md`
- 把过期 handoff 移出活跃区

适合：

- 中型项目后期
- 多 subagent 并行
- 多轮会话开发

## 最小治理闭环

即使只做轻量治理，也建议至少落实以下闭环：

1. 开工前更新 `plan.md`
2. 子任务结束写 `handoff`
3. 阶段结束写 `status`
4. 发版前写 `changelog`
5. 关键长期决策写 `adr`
6. 每次阶段性文档更新后检查 `index.md`
7. 阶段结束后归档旧 `handoff`

## 何时说明治理失效

出现以下情况时，说明文档治理已经开始失效：

- `index.md` 指向的不是最新文档
- 当前阶段有多个 handoff，但没有阶段 `status`
- 旧 handoff 长期停留在活跃目录
- 同一决策在多个文档中相互冲突
- AI 每次都需要重新扫描大量历史文档才能开工

## 推荐落地顺序

对当前项目，建议按这个顺序逐步引入：

1. 建立 `docs/ai/index.md`
2. 建立 `plan`、`handoffs`、`status`、`changelog`、`adr` 目录
3. 明确 `active` 与 `archive` 的 handoff 区分
4. 在模板中加入“更新后检查索引”的规则
5. 后续如有必要，再补一个本地 skill 做自动治理

## 结论

轻量版大项目治理的重点不是把文档做多，而是：

- 用分层控制职责
- 用压缩降低体积
- 用归档隔离历史
- 用 `index.md` 提供当前有效入口

只要这四件事做对，即使没有 Jira、Confluence 或完整知识库系统，项目也能在仓库内部维持相对稳定的 AI 协作文档秩序。
