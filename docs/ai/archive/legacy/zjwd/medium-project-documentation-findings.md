# 中型项目阶段性文档与 Skill 选型发现总结

更新时间：2026-04-15

## 目的

本文档整理本项目关于“在常规 AI 编程与 subagent 并行开发后，生成阶段性文档”的发现与结论，目标是为中型项目建立一套可持续、可接力、可复盘的 AI 协作开发规范。

这里关注的不是单次代码生成能力，而是以下问题：

- 多轮 AI 开发后如何保留真实上下文
- 主 agent 与 subagent 并行后如何顺利接力
- 阶段完成后如何形成结构化记录
- 项目推进中如何同时满足工程接力、进度管理、版本说明三类文档需求

## 结论摘要

对于中型项目，最核心的不是单一“文档 skill”，而是三类能力的组合：

- `session-handoff`：解决工程接力问题
- `status-report`：解决阶段管理问题
- `changelog-automation`：解决版本说明问题

如果只装一个 skill，优先选择 `session-handoff`。

如果要形成比较稳的中型项目 AI 协作规范，推荐组合为：

- `session-handoff`
- `status-report`
- `changelog-automation`

三者分别承担不同职责，不能完全互相替代。

进一步的治理结论如下：

- 文档爆炸是真实风险，尤其在多阶段、多 subagent、多轮会话下几乎必然发生
- 持续治理的核心思路是文档分层、按层压缩、按生命周期归档
- 仅靠 AI 自觉维护 `index.md` 不可靠，最好通过项目规则或自定义 skill 固化
- 对当前这类尚未引入重型工程管理系统的项目，保留一个轻量总索引是有必要的
- 大型项目不是没有索引，而是把索引分散在 issue、PR、ADR、文档首页和搜索系统中

## 已筛选的关键 Skill

### 1. `softaworks/agent-toolkit@session-handoff`

定位：最适合中型项目中的“阶段性工程交接文档”。

适用场景：

- subagent 完成一个独立任务后，向主 agent 回交结果
- 主 agent 完成一个阶段后，给下一轮 AI 或下一位执行者留下上下文
- 中断开发后恢复工作
- 需要减少重复分析和上下文丢失

主要价值：

- 固化当前真实开发状态
- 记录本轮完成项和未完成项
- 记录修改文件与关键实现决策
- 给下一轮 AI 提供明确起点

对中型项目的作用：

- 降低多轮协作的上下文衰减
- 降低 subagent 交付后信息散落的问题
- 减少下一轮 AI 重新“猜测项目状态”

建议用途：

- 每个 subagent 任务结束时生成一次
- 每个阶段结束时由主 agent 生成阶段级 handoff

安装：

```bash
npx skills add https://github.com/softaworks/agent-toolkit --skill session-handoff
```

### 2. `anthropics/knowledge-work-plugins@status-report`

定位：最适合中型项目中的“阶段状态总结”。

适用场景：

- 每周、每阶段、每里程碑需要查看项目状态
- 需要输出进度、风险、阻塞、下一步重点
- 需要把多个 handoff 汇总为项目视图

主要价值：

- 将技术执行信息汇总成项目管理信息
- 帮助判断项目是否按计划推进
- 帮助识别风险、阻塞与优先级

对中型项目的作用：

- 让项目状态从零散实现细节中抽离出来
- 让阶段性复盘有统一结构
- 让后续决策基于结构化信息，而不是基于记忆

建议用途：

- 每个阶段结束时生成一次阶段总结
- 每个里程碑完成时更新一次状态文档

安装：

```bash
npx skills add https://github.com/anthropics/knowledge-work-plugins --skill status-report
```

### 3. `wshobson/agents@changelog-automation`

定位：最适合中型项目中的“阶段变更说明和发布说明”。

适用场景：

- 阶段结束后整理本阶段新增功能和修复项
- 给测试、产品、协作者说明本阶段改了什么
- 需要沉淀阶段级 changelog 或 release notes

主要价值：

- 输出对外可理解的变更说明
- 将工程变更转换为版本级记录
- 方便测试、联调、验收、归档

对中型项目的作用：

- 减少“代码写了，但没人说清楚这一版改了什么”的问题
- 有助于阶段合并、验收和发布前同步

建议用途：

- 每个阶段收尾时生成一次
- 每次准备合并或发布前更新一次

安装：

```bash
npx skills add https://github.com/wshobson/agents --skill changelog-automation
```

定位：偏跨会话记忆。

- 如果项目后续确实依赖 `index.md` 作为 AI 文档入口，最好补一个本地自定义 skill 或项目规则

## 三类 Skill 的职责边界

### `session-handoff` 不是 `status-report`

`session-handoff` 关注的是工程接力，强调：

- 当前代码做到哪里
- 改了哪些文件
- 还有哪些实现没做完
- 下一步应该从哪里继续

它更适合写给下一轮 AI、下一位 agent、下一位工程执行者。

### `status-report` 不是 `changelog`

`status-report` 关注的是阶段健康度，强调：

- 当前阶段目标
- 完成度
- 风险与阻塞
- 下一阶段优先事项

它更适合给项目负责人或自己做阶段管理。

### `changelog-automation` 不是工程 handoff

`changelog` 关注的是变更结果，强调：

- 新增了什么
- 修复了什么
- 是否有破坏性变化
- 本阶段验证了什么

它适合发布、联调、沟通，不适合单独承担工程接力。

## 对中型项目的推荐规范

### 1. 角色分工

中型项目建议采用以下协作模型：

- 主 agent：负责拆解目标、控制阶段边界、汇总阶段结果
- subagent：负责明确、独立、可并行的子任务
- handoff 文档：负责把执行结果转化为可接续上下文
- status 文档：负责把多个任务结果转化为阶段视图
- changelog 文档：负责把阶段成果转化为版本说明

### 2. 阶段性工作流

推荐按以下顺序推进：

1. 主 agent 制定阶段目标和可验收结果
2. 主 agent 将阶段拆分为可并行的 subagent 子任务
3. 每个 subagent 完成任务后输出自己的 handoff 文档
4. 主 agent 汇总所有 handoff，产出阶段 status 文档
5. 阶段准备合并、测试或发布时，生成 changelog 文档

### 3. 文档生成时机

推荐在以下节点强制生成文档：

- 子任务完成后：生成 `handoff`
- 阶段完成后：生成 `status-report`
- 准备联调、合并或发版时：生成 `changelog`

如果项目跨度较大，还应增加：

- 第 0 阶段：生成总计划文档
- 里程碑节点：更新 status 文档
- 长时间中断前：补一次 handoff 文档

## 推荐目录结构

建议在项目中固定使用以下结构：

```text
docs/
  ai/
    plan.md
    handoffs/
      stage-01-auth.md
      stage-01-api.md
      stage-01-ui.md
    status/
      stage-01-summary.md
      stage-02-summary.md
    changelog/
      stage-01.md
      stage-02.md
```

说明：

- `plan.md`：项目级计划与阶段规划
- `handoffs/`：子任务和阶段接力文档
- `status/`：阶段总结和风险视图
- `changelog/`：阶段变更说明

如果后续进入更长期的治理阶段，还建议增加：

```text
docs/
  ai/
    index.md
    archive/
    adr/
```

补充说明：

- `index.md`：当前活跃文档入口，不是全量目录树
- `archive/`：归档已经退出活跃阶段的 handoff 或阶段总结
- `adr/`：长期有效的关键技术与架构决策

## 每类文档的最低内容要求

### A. `plan.md`

建议包含：

- 项目目标
- 范围定义
- 模块划分
- 阶段里程碑
- 核心风险
- 验收标准

作用：

- 给主 agent 和后续 subagent 提供长期边界
- 防止项目过程中目标漂移

### B. `handoff` 文档

每份 handoff 建议至少包含以下 7 项：

- 本任务目标
- 已完成内容
- 修改文件
- 关键实现决策
- 当前未完成项
- 已知风险或坑
- 下一位 agent 的第一步动作

作用：

- 保证 subagent 交付后不是只交代码
- 降低主 agent 汇总成本
- 让下一轮工作具备清晰起点

### C. `status-report` 文档

每份状态文档建议至少包含以下 5 项：

- 当前阶段目标
- 当前完成度
- 风险与阻塞
- 下一阶段重点
- 是否达到阶段验收条件

作用：

- 帮助判断项目推进是否健康
- 帮助决定下一阶段资源和优先级

### D. `changelog` 文档

每份变更说明建议至少包含以下 4 项：

- 新增功能
- 修复问题
- 破坏性变更
- 测试或验证范围

作用：

- 对外同步本阶段实际交付
- 方便测试、联调和版本回顾

## 一个中型项目的示例节奏

以一个中型 SaaS 项目为例：

### 第 0 阶段：架构和骨架

主 agent 负责：

- 梳理目标和范围
- 建立模块边界
- 确定数据库、API、前端、部署等技术路线
- 生成 `docs/ai/plan.md`

### 第 1 阶段：认证、用户、基础 API

subagent 可按功能拆分：

- subagent A：认证与登录流程
- subagent B：用户模型与数据库迁移
- subagent C：API 路由、鉴权、中间件、错误处理

该阶段要求：

- 每个 subagent 完成后提交对应 handoff
- 主 agent 汇总形成 `stage-01-summary.md`

### 第 2 阶段：核心业务流

延续相同模式：

- 将业务流拆给多个 subagent
- 每个子任务结束后生成 handoff
- 阶段收尾生成 status
- 联调前生成 changelog

### 第 3 阶段：测试、性能、部署

可拆为：

- subagent A：测试补齐
- subagent B：性能优化
- subagent C：CI/CD 与部署

该阶段重点：

- handoff 中记录遗留风险和部署注意事项
- status 中记录上线风险和阻塞
- changelog 中记录上线前最终变化

## 为什么这套规范对中型项目必要

中型项目的特点是：

- 不会一次完成
- 往往需要多轮 AI 协作
- 往往需要多线程推进
- 容易在阶段切换时丢上下文

如果没有阶段性文档，常见问题包括：

- 下一轮 AI 重复分析已有实现
- subagent 输出只有代码，没有上下文
- 项目状态无法快速判断
- 版本变化缺少结构化记录
- 中途暂停后恢复成本高

采用上述规范后，收益主要体现在：

- 并行开发不容易失控
- 切换线程后仍能无缝续上
- 阶段状态可复盘
- 项目风险更早暴露
- 发布说明与工程过程形成闭环

## 文档爆炸问题的判断

### 文档爆炸会不会发生

会。

对中型项目而言，只要同时出现以下三项中的两项以上，文档爆炸就大概率会发生：

- 多阶段推进
- 多个 subagent 并行
- 多轮会话持续开发

最容易膨胀的是 `handoff` 类文档，因为它们天然是高频、短周期、面向接力的记录。

### 文档爆炸为什么危险

危险不在于文档数量本身，而在于：

- 当前有效入口不明确
- 历史上下文和当前上下文混杂
- AI 或人类执行者不知道先看哪份
- 同类信息在多个地方重复出现
- 文档集合开始消耗维护成本，但不再提供等价价值

### 持续治理的核心是不是“分层 + 压缩”

是，但要补上生命周期管理。

更准确的表达应是：

- 分层：按用途拆成不同类型的文档层
- 压缩：把低层高频记录持续汇总成高层摘要
- 归档：把退出活跃阶段的文档移出主入口
- 索引：为当前仍然有效的文档提供可检索入口

也就是说，持续治理不是单独“压缩”，而是：

`分层 -> 压缩 -> 归档 -> 保留活跃入口`

## 是否需要总索引文件

### 是否还需要一个总的索引文件

需要，尤其在当前项目还没有 Jira、Linear、Confluence、成熟 ADR 体系或统一知识库搜索的前提下。

原因：

- AI 需要一个稳定入口来判断当前先读什么
- 新一轮会话需要快速定位当前有效文档
- 索引能阻止 AI 把归档文档和活跃文档混为一谈

### 这个索引应该是什么样

建议是“轻索引”，不是“全量树”。

推荐 `docs/ai/index.md` 只维护以下内容：

- 当前阶段
- 当前主目标
- 最新有效的 `plan`
- 最新有效的 `handoff`
- 最新有效的 `status`
- 最新有效的 `changelog`
- 历史归档入口

不建议让 `index.md` 维护全量文件列表，否则索引本身会变成新的膨胀源。

### 不使用 skill，AI 会不会自动维护 `index.md`

不能稳定指望。

如果没有以下任一机制，AI 不会可靠地把更新 `index.md` 作为每轮对话的固定收尾动作：

- 项目明确规则
- 自定义 skill
- 自动化流程

因此，`index.md` 想真正发挥作用，最好配套以下至少一项：

- 项目约定：每次实质性进展后同步检查 `index.md`
- 自定义 skill：在生成 `handoff` / `status` / `changelog` 后自动要求维护索引
- 自动化脚本：定期校验索引是否指向最新有效文档

## 大型项目为什么不总是显式使用 `index.md`

大型项目并不是没有文档爆炸问题，而是通常依靠更大的一套治理系统来分担。

常见做法包括：

- 用清晰目录结构、接口、测试、类型系统让代码本身成为第一记忆层
- 用 issue 和 PR 做任务与变更索引
- 用 ADR 做长期决策记录
- 用 changelog 和 runbook 管理发布与操作信息
- 用搜索和知识库代替“记住所有上下文”

因此，大型项目不是不需要索引，而是索引已经分散在多个治理系统里。

对当前项目而言，这些重型系统还没有建立，所以保留一个 `docs/ai/index.md` 作为轻量统一入口是合理且必要的过渡方案。

## 推荐采用的最小闭环

### 最小方案

仅安装并使用：

- `session-handoff`

适合刚开始引入阶段性文档规范的项目。

### 稳定方案

安装并使用：

- `session-handoff`
- `status-report`

适合绝大多数中型项目。

### 完整方案

安装并使用：

- `session-handoff`
- `status-report`
- `changelog-automation`

适合需要阶段验收、联调、发布归档的中型项目。

## 实施建议

### 建议一：文档生成要制度化

不要把文档生成当作“有空再做”的补充动作，而应作为阶段完成条件的一部分。

建议把以下规则固定下来：

- 子任务完成，不只提交代码，还必须提交 handoff
- 阶段结束，不只看功能，还必须更新 status
- 准备合并或发版，不只看提交记录，还必须更新 changelog

### 建议二：主 agent 只负责汇总，不代替 subagent 回忆

最佳实践是每个 subagent 在任务结束时立刻产出 handoff，主 agent 只负责整合和抽象，不负责替每个 subagent 补回忆。

这样可以减少信息损耗。

### 建议三：文档要服务于下一步动作

阶段性文档不能只写“做了什么”，还必须明确“接下来最该做什么”。

尤其 handoff 中必须明确：

- 当前缺口
- 下一步动作
- 起始文件或模块
- 需要注意的约束

## 最终推荐

对于本项目后续如果按中型项目推进，建议采用以下规范：

1. 建立 `docs/ai/` 目录作为 AI 协作文档根目录
2. 先建立 `plan.md` 作为总计划文档
3. 每个 subagent 任务结束后生成 handoff 文档
4. 每个阶段结束后生成 status 文档
5. 每次准备联调、合并或发版前生成 changelog 文档
6. skill 组合优先采用 `session-handoff + status-report + changelog-automation`

这套规范的核心目标不是增加文档数量，而是降低 AI 协作中的上下文损耗，并把中型项目推进过程转化为可持续、可接力、可审查的结构化资产。
