# V2 文档项目的 REQDOC / REQ / WS / STAGE 拆解模板

更新时间：2026-04-19
适用范围：你已经有现有项目代码和 V2 版本文档，准备基于这批文档推进新版本开发

## 四个对象分别是什么

### REQDOC

`REQDOC` 是原始需求包。

它通常对应：

- 一份 PRD
- 一份版本说明
- 一个模块设计稿集合
- 一组会议纪要整理稿

它保留来源语义，不负责开发拆解。

### REQ

`REQ` 是可验收的标准化需求单元。

一条 `REQ` 应该满足：

- 目标单一
- 范围明确
- 有验收条件
- 能被实现和验证直接引用

### WS

`WS` 是可开发的垂直工作流。

它不是文档章节，也不是人力任务清单，而是“能形成业务闭环的一条实现流”。

一个 `WS` 往往会覆盖多条 `REQ`。

### STAGE

`STAGE` 是阶段压缩和执行顺序，不是需求类型。

它回答的是：

- 先做什么
- 后做什么
- 哪些成果已经稳定到值得压缩

## 拆解原则

- `REQDOC` 按来源文档分，不按技术模块分
- `REQ` 按验收单元分，不按页面 section 分
- `WS` 按垂直交付流分，不按前端/后端人力边界分
- `STAGE` 按验证和压缩顺序分，不按组织架构分

## 推荐拆解流程

### Step 1. 先整理 V2 输入包

先把 V2 相关文档按来源收拢。

例如：

- V2 总体 PRD
- 用户中心改版文档
- 支付流程改版文档
- 数据迁移说明

这一步的产出通常是多个 `REQDOC` 候选。

### Step 2. 建立 REQDOC

一个来源包建一个 `REQDOC`。

建议命名方式：

- `REQDOC-001-v2-overview.md`
- `REQDOC-002-v2-user-center.md`
- `REQDOC-103-v2-payment-flow.md`

示例中的 100 段编号用于表示另一个来源批次，避免和当前项目真实 `REQDOC / REQ / WS` 编号混淆；实际项目按本地编号规则分配。

适合单独建 `REQDOC` 的信号：

- 来源不同
- 负责人不同
- 上线节奏不同
- 业务主题不同

### Step 3. 从 REQDOC 拆 REQ

拆 `REQ` 时，不要按目录标题机械拆。

应该按“是否能独立验收”来拆。

一条合格的 `REQ` 通常像这样：

- 用户可以查看新版个人资料摘要
- 用户可以编辑昵称和头像
- 系统在保存后返回更新后的资料快照
- 管理后台可以看到本次变更记录

不建议这样拆：

- 页面顶部区域
- 页面中部区域
- 按钮样式调整

那样拆出来的是 UI 碎片，不是需求单元。

### Step 4. 从 REQ 归并 WS

把能形成一条业务闭环的 `REQ` 放进同一个 `WS`。

示例：

- `WS-01 用户资料查看与编辑`
  - `REQ-001 查看资料摘要`
  - `REQ-002 编辑昵称头像`
  - `REQ-003 保存后返回新快照`

- `WS-02 资料变更审计`
  - `REQ-004 写入变更日志`
  - `REQ-005 后台查询变更记录`

判断是否应属于同一 `WS`，看这几件事：

- 是否服务同一用户路径
- 是否适合一次端到端验证
- 是否可以在一次迭代里交付

## `STAGE` 怎么定

`STAGE` 不要跟 `WS` 一一绑定死。

更好的方式是：

- `STAGE-00`：先打通首条关键链路
- `STAGE-01`：扩展第二批工作流并补验证
- `STAGE-02`：补性能、治理、CI、回归

也就是说：

- `REQ` 是“做什么”
- `WS` 是“按什么闭环做”
- `STAGE` 是“按什么顺序做并压缩成果”

## 一个 V2 项目的推荐映射示例

| V2 文档来源 | REQDOC | REQ | WS | STAGE |
| --- | --- | --- | --- | --- |
| V2 总体 PRD | `REQDOC-001` | `REQ-001` 登录体验统一；`REQ-002` 首页导航重构 | `WS-01 统一登录入口` | `STAGE-00` |
| 用户中心改版 | `REQDOC-002` | `REQ-003` 资料摘要；`REQ-004` 资料编辑；`REQ-005` 保存反馈 | `WS-02 用户资料闭环` | `STAGE-00` |
| 审计后台说明 | `REQDOC-103` | `REQ-106` 审计日志写入；`REQ-107` 审计查询 | `WS-13 审计与追踪` | `STAGE-01` |

## 文件落地模板

### REQDOC 模板

适合写这些信息：

- 文档编号
- 来源
- 背景
- 原始目标
- 关键范围
- 不明确点

### REQ 模板

每条 `REQ` 至少写清：

- 背景
- 目标
- 范围
- 验收条件
- 依赖与前置条件

### WS 模板

每个 `WS` 至少写清：

- 使用边界
- 业务目标
- 覆盖需求
- 主要模块
- 阶段拆分建议
- 验收模型

### traceability-matrix

至少能回答：

- 这条实现对应哪个 `REQDOC`
- 它落到了哪些 `REQ`
- 它属于哪个 `WS`
- 当前在哪个 `STAGE`
- 验收/测试证据是什么

## 基于 harness 推进 V2 开发的推荐工作流

拆完以后，不要再回到“直接和 AI 聊一个大版本”。

更好的方式是每轮都围绕一组明确的 `REQ / WS`：

1. 先指定当前轮要做的 `WS`
2. 让 AI 先读 `index / working-context / requirements index / traceability`
3. 再读该 `WS` 覆盖的 `REQ`
4. 实现一个垂直切片
5. 完成后补 `handoff`
6. 同步 `traceability-matrix`
7. 阶段结束再压 `status`

## 可直接给 AI 的开发 Prompt

```text
基于当前 V2 文档和现有代码，不要同时铺开整个版本。
先按 harness 规则推进：
1. 盘点当前 V2 文档来源，并建立对应 REQDOC
2. 把当前最关键的一组需求拆成可验收的 REQ
3. 把这组 REQ 归并成一个可端到端交付的 WS
4. 更新 traceability-matrix 与 working-context
5. 然后只实现这个 WS 的第一个垂直切片
6. 完成后补 handoff，并给出下一阶段建议
```

## 常见误区

- 把 `REQDOC` 当成开发任务
- 把 `REQ` 拆成纯 UI 碎片
- 把 `WS` 拆成前端任务 / 后端任务
- 把 `STAGE` 写成永远不压缩的长期清单
- 只写代码，不同步 `traceability-matrix`

## 判断拆解是否合理

如果一轮开发结束后，你能明确回答这 4 个问题，拆解通常就合理：

- 这次功能来自哪份 V2 原始文档
- 它被标准化成了哪些 `REQ`
- 它属于哪个 `WS`
- 它当前在什么 `STAGE`，并且已经有哪些验收证据
